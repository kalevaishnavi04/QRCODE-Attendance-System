# QR Code Attendance System

> **How can classroom attendance be automated to reduce manual effort, prevent duplicate attendance, and give teachers real-time attendance visibility?**

A smart, QR-based attendance management system built with Django that allows teachers to create **time-limited attendance sessions**, students to mark attendance by scanning a QR code, and administrators to manage students, subjects, attendance records, and reports.

🔗 **Live Demo:** https://qr-code-attendance-system-l04f.onrender.com
💻 **GitHub:** https://github.com/kalevaishnavi04/QR_code-Attendance-System

---

# 1. Business Context

## Problem

Traditional classroom attendance is often recorded manually through roll calls or spreadsheets. This process can consume valuable classroom time, make attendance records difficult to manage, and provide limited visibility into attendance trends.

There is also a risk of duplicate or proxy attendance when the same attendance mechanism is reused across multiple sessions.

## Project Objective

The objective of this project was to build a centralized attendance management system that:

* Automates attendance collection using QR codes
* Creates a unique QR code for every class session
* Automatically expires QR codes after a defined period
* Prevents students from marking attendance multiple times
* Provides teachers with real-time attendance statistics
* Allows attendance records to be exported to Excel
* Provides administrators with centralized data management

My responsibilities included:

* Designing the database structure

## Business Decision

The key design decision was to replace static/manual attendance collection with **session-based QR attendance**.

Instead of using one permanent QR code, the system generates a new QR code for each class session. This creates a direct relationship between:

**Student → Subject → Class Session → Attendance Record**

# 2. Data Source & Data Model

## Data Source

This project does not use a static CSV or external analytics dataset.

The attendance dataset is **generated by the application itself** whenever students successfully mark attendance.

The system stores operational data related to:

* Students
* Class years
* Subjects
* Teachers
* Attendance sessions
* Attendance records

## Data Grain

The primary attendance data grain is:

> **One attendance record represents one student attending one class session.**

For example:

```text
Student: 101
Subject: Data Science
Session: DS_2026_08_09_01
Attendance: Present
Timestamp: 2026-08-09 10:15
```

This grain allows attendance to be analyzed at:

* Student level
* Subject level
* Class-year level
* Session level
* Date level

## Time Span

The time span is **dynamic** because attendance records are generated as the application is used.

The system can therefore support attendance analysis across:

* Daily attendance
* Weekly attendance
* Monthly attendance
* Semester-level attendance
* Academic-year attendance

## Data Volume

The data volume is also dynamic and depends on the number of:

* Registered students
* Subjects
* Attendance sessions
* Attendance events

The application is designed to support growing attendance records through a relational database.

## Schema

| Entity             | Grain                          | Important Fields                  | Purpose                            |
| ------------------ | ------------------------------ | --------------------------------- | ---------------------------------- |
| Class Year         | One record per class year      | ID, Name                          | Groups students academically       |
| Subject            | One record per subject         | ID, Name, Class Year, Teacher     | Defines academic subjects          |
| Student            | One record per student         | ID, Name, Roll Number, Class Year | Stores student information         |
| Attendance Session | One record per class session   | ID, Subject, Created At, Expiry   | Represents a QR attendance session |
| Attendance         | One record per student/session | Student, Session, Timestamp       | Stores attendance events           |
| Teacher            | One record per teacher         | ID, Name, Login Details           | Manages attendance sessions        |

# 3. Methodology

## 3.1 Dynamic QR Code Generation

Teachers can create an attendance session by selecting the relevant class year and subject.

The system generates a unique QR code associated with that specific session.

```text
Teacher
   ↓
Select Class Year
   ↓
Select Subject
   ↓
Create Session
   ↓
Generate QR Code
   ↓
Students Scan
```

### Why this approach?

A static QR code could potentially be reused outside the intended attendance session.

Dynamic QR generation creates a unique attendance context for each class.

**Technology:** `qrcode`, `Pillow`

---

## 3.2 Time-Limited Sessions

Each attendance session has a defined validity period.

Once the session expires, the QR code can no longer be used to submit attendance.

```text
Session Created
      ↓
QR Active
      ↓
Student Scans
      ↓
Session Valid?
   ↙       ↘
 YES        NO
 ↓           ↓
Continue    Reject
```

### Why?

Time-based validation reduces the possibility of students using an old QR code to mark attendance later.

---

## 3.3 Student Validation

After scanning the QR code, students provide their roll number.

The system validates the attendance request against the active session and registered student information.

The workflow is:

```text
QR Scan
   ↓
Session Validation
   ↓
Roll Number
   ↓
Student Validation
   ↓
Duplicate Check
   ↓
Attendance Created
```

---

## 3.4 Duplicate Prevention

The system checks whether the student has already marked attendance for the current session.

```text
Student + Session
       ↓
Already Exists?
   ↙          ↘
 YES           NO
 ↓              ↓
Reject       Create Record
```

### Why?

This prevents multiple attendance records for the same student within the same class session.

The expected logical rule is:

```text
One Student + One Session = One Attendance Record
```

---

## 3.5 Class Year & Subject Filtering

The application supports dependent selection between class year and subject.

Example:

```text
TY
├── Data Science
├── Machine Learning
└── Cloud Computing
```

Teachers can select the appropriate class and subject before generating the attendance session.

### Why?

This reduces incorrect subject/session selection and ensures attendance is associated with the correct academic group.

# 4. Key Findings

Since this project is an operational application rather than a historical analytics dataset, the findings focus on **system outcomes and workflow improvements** rather than fabricated numerical business results.

## Finding 1 — Attendance Collection Can Be Digitized

The QR workflow replaces manual roll-call attendance with a digital process.

```text
Manual Process

Teacher → Calls Names → Records Attendance → Calculates Total


QR Process

Teacher → Generates QR → Student Scans → Attendance Recorded
```

This reduces repetitive manual data entry.

---

## Finding 2 — Attendance Is Linked to a Specific Session

Every attendance record is connected to a particular attendance session.

This creates a structured relationship:

```text
Student
   ↓
Attendance
   ↓
Session
   ↓
Subject
   ↓
Class Year
```

This structure makes attendance records easier to audit and analyze.

---

## Finding 3 — Duplicate Attendance Can Be Controlled

The duplicate-validation mechanism ensures that a student cannot create multiple attendance records for the same session.

This improves data quality by preventing repeated records.

---

## Finding 4 — Time-Limited QR Codes Improve Session Control

QR codes are associated with individual attendance sessions and have a limited validity period.

This provides better control than a permanent QR code because an expired session cannot continue accepting attendance submissions.

---

## Finding 5 — Attendance Data Becomes Immediately Reportable

The dashboard provides immediate attendance visibility, while Excel export allows the underlying records to be used for additional analysis.

The workflow becomes:

```text
Attendance Event
       ↓
Database
       ↓
Dashboard
       ↓
Excel Report
       ↓
Further Analysis
```

# 6. Limitations & Assumptions

## Limitations

### 1. QR Code Does Not Guarantee Physical Presence

A QR code confirms that a student submitted attendance through the session.

It does not independently prove that the student was physically inside the classroom.

**Potential improvement:** GPS/geofencing or classroom-based network validation.

---

### 2. Roll Number Is Not Strong Identity Verification

If the system relies on students entering their roll number, the system cannot completely prevent someone from entering another student's roll number.

**Potential improvement:** authenticated student accounts or institutional login.

---

### 3. Internet Connectivity Is Required

Students need access to the application while scanning the QR code and submitting attendance.

Poor network connectivity may affect attendance submission.

---

### 4. Dashboard Insights Depend on Data Quality

Incorrect student registration, incorrect subject assignment, or incorrect session creation can affect attendance reporting.

---

### 5. SQLite Is Not Ideal for Large Production Workloads

SQLite is convenient for local development.

For production environments with many concurrent users, PostgreSQL is more appropriate.

---

## Assumptions

The system assumes:

* Each student has a unique roll number.
* Students are correctly registered under their class year.
* Subjects are correctly assigned to class years.
* Teachers create the correct attendance session.
* Students scan the QR code during the intended class.
* Users have access to a compatible device and network connection.
* Administrators maintain accurate student and subject data.

# 8. Reproduce the Project

## Step 1 — Clone Repository

```bash
git clone https://github.com/kalevaishnavi04/QR_code-Attendance-System.git
```

Navigate to the Django project:

```bash
cd QR_code-Attendance-System/attendance_system
```

---

## Step 2 — Create Virtual Environment

### Windows

```bash
python -m venv venv
venv\Scripts\activate
```

### macOS/Linux

```bash
python -m venv venv
source venv/bin/activate
```

---

## Step 3 — Install Dependencies

```bash
pip install -r requirements.txt
```

---

## Step 4 — Run Database Migrations

```bash
python manage.py migrate
```

```bash
python manage.py createsuperuser
```

```text
Password
```
